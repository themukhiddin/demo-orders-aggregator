## Что сделано

Каждое исправление — отдельный коммит с тестом. На коде до исправления тест падает.

1. **Летнее время при разбивке по дням** (`services/totals.ts`). Это основная причина расхождения из жалобы, подробности ниже.
2. **Атомарное применение версий заказа** (`repositories/orders.ts`, `services/orders.ts`). Это вторая причина расхождения.
   - Было: проверка «новее ли версия» (`SELECT`) и запись (`UPSERT`) шли двумя запросами.
   - Стало: один `INSERT … ON CONFLICT DO UPDATE … WHERE orders.updated_at < excluded.updated_at`. Создан заказ, обновлён или версия устарела, определяется по `RETURNING`.
3. **Перевод рублей в копейки без потери копейки** (`utils/money.ts`).
   - Было: `Math.floor(rub * 100)`. Для части сумм это давало на копейку меньше, например `4723.9 * 100 = 472389.99999999994`.
   - Стало: погрешность float убирается до отбрасывания долей. Задокументированное поведение «доли копейки отбрасываются» сохранено.
   - Для `amount` это не проявлялось, суммы там целые. Но у 101 значения `amountPaid` в данных API ошибка была бы.
4. **Скидки в `daily-totals`.**
   - Миграция `002_paid_kop.sql` добавляет колонку `orders.paid_kop`: сколько фактически оплачено, в копейках, с `CHECK 0 ≤ paid_kop ≤ amount_kop`.
   - `gross` — сумма `amount_kop`, `net` — сумма `paid_kop`, `discount = gross − net`, `total = gross`. Всё считается в целых копейках, в рубли переводится только в ответе.
   - `discount` не хранится, а вычисляется, поэтому `gross = net + discount` выполняется всегда.
   - Валидация: `amountPaid` и `discountPercent` принимаются числом или строкой, как и `amount`. Отрицательный, нечисловой или больший `amount` `amountPaid` — ошибка валидации: вебхук получает 400, а синк учитывает такой заказ в `invalid`.
5. **Ответ `daily-totals` в существующих тестах.** В ожидаемый ответ дописаны новые поля. Значения `total` не менялись: заказы в этих тестах без скидки, поэтому `gross = net = total`, `discount = 0`.
6. **README.** Обновлены описание ответа `daily-totals` и раздел о полях скидки.

Тестов было 27, стало 41. Все проходят, `tsc --noEmit` без ошибок.

## Причина расхождения по c_7

Причин две.

### 1. Смещение таймзоны бралось «на сейчас», а не на момент заказа

В `TotalsService.daily` стояло `tzOffsetMinutes(timezone, new Date())`, и одно смещение применялось ко всем заказам периода.
- У `c_7` таймзона `Europe/Berlin`. Сейчас (ноябрь) там UTC+1, а с 29.03.2026 01:00 UTC — UTC+2.
- Поэтому оплаченные заказы, созданные с 22:00 до 23:00 UTC 29–31 марта, попадали в предыдущий день.
- 27 и 28 марта ещё до перехода, поэтому они сходились, а 29–31 — нет. Это и есть «часть дней».

| Заказ | Сумма | Создан (UTC) | День в Берлине | Сервис относил к |
|---|---|---|---|---|
| o_02357 | 9306 | 29.03 22:40 | 30.03 | 29.03 |
| o_02448 | 1823 | 30.03 22:40 | 31.03 | 30.03 |
| o_02547 | 4999 | 31.03 22:40 | 01.04 | 31.03 |
| o_02545 | 5487 | 31.03 22:15 | 01.04 | 31.03 (стал `paid` по вебхуку) |

Обратите внимание: результат старого кода зависел от того, в какой день его запускать. Летом он ошибался бы на зимних датах.

Теперь смещение считается на момент создания каждого заказа. Форматтер `Intl.DateTimeFormat` кешируется по таймзоне.

Тест содержит заказы по обе стороны перехода. Поэтому он падает на старом коде при любом «сейчас»: и зимой, и летом.

### 2. Гонка при параллельных вебхуках

Внешняя система шлёт вебхуки параллельно: я замерил до 6 одновременных запросов. Разные версии одного заказа часто попадают в одну пачку.
- Пример: у o_02281 (создан 29.03) вебхуки #86–91 одновременно несут версии `refunded` и `paid`.
- При двух запросах (проверка, потом запись) старая версия `paid` иногда затирала новую `refunded`, и 29.03 вырастал на 3675 ₽.
- Это проявлялось не на каждом прогоне. Возможно, поэтому расхождение у аналитиков было плавающим.

### Как нашёл

1. **Чтение кода.** Нашёл подозреваемых: смещение на `new Date()`, `Math.floor` в `toKop`, условие остановки синка, трактовку дат без зоны как UTC.
2. **Выгрузка API.** Выгрузил все заказы из внешнего API своим скриптом, в обход сервиса, с логом страниц. Пагинация в порядке: 5030 заказов, пустая страница только в конце. Подозрение на синк снято.
3. **Перехват вебхуков.** Поднял свой HTTP-приёмник и прогнал на него вебхуки: 92 события, 21 заказ, все относятся к `c_7`, с повторами и не по порядку.
4. **Эталон.** Посчитал независимый эталон: синк плюс самая свежая по `updatedAt` версия каждого заказа, день по `Europe/Berlin` на момент заказа через `Intl`.
5. **Сравнение.** Прогнал полный сценарий на исходном коде трижды. Разница с эталоном по дням целиком объяснялась заказами из таблицы выше.
6. **Гонка.** После исправления таймзоны очередной прогон дал 29.03 на 3675 ₽ больше эталона. Это o_02281. Тогда я замерил параллельность отправителя: сделал приёмник, отвечающий с задержкой 300 мс, и увидел максимум 6 одновременных запросов. Воспроизвёл гонку тестом: 6 параллельных вебхуков с разными версиями падали стабильно.

## Как проверял результат

При работе использовался ИИ-ассистент. Ни один вывод не принимался без проверки на данных:

- **Тесты.** Для каждого исправления сначала писал тест и убеждался, что он падает на старом коде, затем исправлял.
- **Эталон.** Эталон считался независимо от кода сервиса: по сырым ответам API и перехваченным вебхукам. Полный сценарий (чистая БД → `/sync` → вебхуки → `daily-totals`) прогнан 5 раз после исправления гонки и ещё 4 раза после добавления скидок, включая финальный прогон для `result.json`. Каждый раз ответ совпадал с эталоном по всем полям до копейки.
- **Данные.** `amountPaid` во всех 3945 версиях заказов, где он есть, совпадает с `amount × (1 − discountPercent/100)` до копейки.
- **`toKop`.** Проверен перебором: все суммы от 0 до 100 000 ₽ с шагом в копейку переводятся без ошибок.
- **Миграция на непустой БД.** Применил миграцию на БД с 5030 заказами по старой схеме, затем `/sync`: `paid_kop` дозаполнен у 5009. Про оставшиеся 21 — в разделе «Что бы доделал».

## Что ещё заметил

### Внешний API
- **Вебхуки.** Приходят параллельно (до 6 одновременно), с повторами (до 6 раз) и не по порядку. Это учтено.
- **`/orders` отстаёт.** Список отдаёт не самую свежую версию заказа: у 21 заказа вебхуки новее. Самая свежая версия приходит только вебхуком.
- **`amountPaid` меняется между версиями при том же статусе.** Например, у o_02362: 5904 → 5313.6 → 3955.68. Скидка может пересчитываться после оплаты.
- **Плавающие типы:**
  - `amount` иногда строка (`"4999.00"`);
  - `discountPercent` иногда строка (`"15"`);
  - у 288 заказов `createdAt` без зоны (`"2026-03-29T01:45:18"`). Я проверил, что такие времена ложатся на ту же суточную сетку UTC, что и времена с `Z`, поэтому трактовка «без зоны = UTC» верна;
  - у 1177 заказов нет полей скидки.
- **Лимит запросов.** Превышение приходит как `200 {"error":"rate_limited"}` без `Retry-After`. Клиент это обрабатывает.

### Код
- **Сервис не читает `.env`.** Без явного экспорта переменных и сервис, и тесты идут на `localhost:5432`. Тесты делают `TRUNCATE`, и если на этом порту окажется другая БД (у меня так и было), её данные будут стёрты. Стоит запускать через `node --env-file=.env` и не держать для тестов значения по умолчанию.
- **Таймзона клиента кешируется навсегда.** Так сделано намеренно, это проверяет тест. Но если клиент сменит таймзону, сервис об этом не узнает.
- **Возвраты меняют прошлые дни.** Заказ, возвращённый позже, задним числом пропадает из суммы дня оплаты, и отчёты за прошлые дни меняются. Для сверки с платёжной системой это, видимо, верно, но об этом стоит знать.
- **`POST /sync` синхронный** и из-за лимита API (52 страницы при 4 rps) идёт не меньше 13 секунд. Если внешний API ответит нештатной ошибкой посреди синка, весь синк падает, а продолжить с места остановки нельзя.

## Допущения

- **День заказа** — по `createdAt` в таймзоне клиента, как было. Жалоба подтверждает, что остальные дни сходятся, значит, платёжная система считает так же.
- **`net` берётся из `amountPaid`**: это «сколько фактически заплатили». `discountPercent` используется только при отсутствии `amountPaid`. Если они не сходятся, верим `amountPaid`.
- **Нет `amountPaid` и `discountPercent`** — заказ до появления скидок, считается без скидки: `net = gross`.
- **Оплата из `discountPercent`** считается с отбрасыванием долей копейки, как в `toKop`. На текущих данных доли не возникают.
- **Некорректный `amountPaid` или `discountPercent`** (больше `amount`, отрицательный, нечисловой) делает весь заказ невалидным. Так же сервис уже поступал с некорректным `amount`.
- **`discount` — это `gross − net`**, а не сумма процентов по заказам.

## Что бы доделал

- **Дозаполнить `paid_kop` после миграции на существующей БД.** Повторный `/sync` заполняет строки, у которых версия в БД совпадает с версией в `/orders`. Но 21 заказ, обновлённый вебхуками, в `/orders` представлен более старой версией. Брать из неё `amountPaid` нельзя, потому что он меняется между версиями. Такие строки до следующего вебхука считаются без скидки. Варианты:
  - эндпоинт внешнего API для получения текущей версии заказа;
  - хранить сырые события вебхуков и переигрывать их.
- **Считать дни в SQL** (`created_at AT TIME ZONE tz`) вместо загрузки всех заказов в память. Для длинных периодов это быстрее.
- **Хранить сырые события вебхуков** для аудита и повторной обработки.
- **Загружать `.env`** через `node --env-file` и не использовать значения по умолчанию для тестовой БД.
- **Асинхронный `/sync`** со статусом и возобновлением с последнего курсора.
- **Метрики** stale и invalid для синка и вебхуков, чтобы видеть проблемы внешнего API.
